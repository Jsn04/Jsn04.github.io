SkillMatch v2

A matching layer across your own bench and the open market, ranked by fit — not keywords.

SkillMatch started as an internal staffing tool: describe a project, get your own engineers ranked by fit. v2 extends it into a two-sided hiring marketplace — same matching engine, same explainable scores, but now open to external engineers and companies too. The differentiator is the bridge: when your bench can't cover a project, one click sends the same search to the external pool. No job board has that because no job board also owns your bench.

Design

Three User Types, One Engine

The three actors each have separate portals, scoped tokens, and role-guarded endpoints. They share a single matching engine and the same mutual-connect loop.

Internal Manager

Staffs their company's bench to projects via k-NN. When the bench falls short, bridges to the external pool with one click — same search, different pool.

External Company

Posts openings, receives ranked engineer profiles with explainable match scores. Expresses interest; contact only unlocks when both sides match.

Engineer

Builds a candidate profile with skills and resume. Matched to open roles, sees a ranked inbox of companies, connects only on mutual interest.

Core Algorithm

Two Matching Engines

Internal and external hiring are fundamentally different problems. The two engines reflect that — but they share the same scoring function so a match always means the same thing on both sides.

Internal · recommender.py
k-NN over 5 numeric levels

Managers rate engineers on seniority, domain, communication, timezone, and bandwidth. Euclidean distance = exact fit for immediate placement (excludes fully-booked). Cosine = potential fit for scouting (keeps them, shows availability). Filtered by discipline and vertical.

External · openings.py score()
Weighted sum out of 100 — explainable

External strangers' self-ratings are worthless, so the external engine judges by real candidate evidence. Runs both directions from the same function — a company ranking engineers and an engineer ranking openings never disagree on what a good match is.

ML

Semantic Skill Matching

The original scorer used exact string matching — React ≠ React.js, Postgres ≠ PostgreSQL, k8s ≠ Kubernetes. A perfect candidate could rank near the bottom on spelling alone. matching_ai.py fixes this in three layers, most-reliable-first.

1
Alias map
Curated common synonyms: react.js→react, k8s→kubernetes, postgres→postgresql. Deterministic, always right, handles most real-world cases with zero inference cost.
2
Exclusivity groups
The false-friend guard. A general embedding model rates MySQL/MongoDB, React/Angular, AWS/Azure as "similar" — they're alternatives, not the same skill. Two members of the same exclusivity group (databases, clouds, frontend frameworks, languages) never match, regardless of embedding similarity.
3
Embedding model
BAAI/bge-small-en-v1.5 via fastembed (ONNX, local, no external API). Safety net for the long tail above a tuned 0.80 similarity threshold. Model baked into the Docker image — runs fully offline, no candidate data leaves the box. Validated at 42/42 on a labeled set (23 synonyms that must match, 19 false-friends that must not).

Real before/after: an engineer who wrote "Postgres/AWS/k8s" jumped 83%→100% on a role asking for "PostgreSQL/AWS/Kubernetes". Engineers who already matched exactly were unchanged — matches never get worse. Behind a kill-switch: SEMANTIC_MATCHING=off falls back to exact matching instantly.

Security

Security Model

  • Hard role separation: engineer token → company endpoint = 403; company token → engineer endpoint = 403; internal-manager token → any marketplace endpoint = 403. Enforced by require_company / require_engineer / current_user guards. Verified end-to-end.
  • Contact locked until mutual: before both sides express interest, a company sees the engineer's profile but email = "" and the resume endpoint returns 403. Cross-company isolation verified — Company B cannot see Company A's unlocked contacts.
  • Bridge org security: a manager's org gets a company identity auto-provisioned on first post, derived from their email domain. Login-disabled (sentinel password hash) and never attached to a pre-existing company account — prevents anyone hijacking an org's openings by registering first.
  • Passwords: PBKDF2 + per-user salt, constant-time comparison. CORS locked to configured origins. SECRET_KEY refuses to boot outside dev if unset.
